Oui, le séquencement est le bon — construire d'abord dans le concret (le site CNT), généraliser ensuite (clyro-blocks + theming). C'est exactement le bon ordre : extraire un composant depuis un vrai cas d'usage donne toujours une meilleure API que de le concevoir dans l'abstrait. Trois précisions pour que ça se passe bien :
1. Il existe déjà un bloc Navbar dans clyro-blocks (un des 8 blocs de la v1, style Clyro fixe). Ta navbar CNT ne sera donc pas le « premier » composant navbar, mais la deuxième variante — et c'est justement ça qui est intéressant : c'est au moment où une catégorie a 2 variantes avec des styles différents qu'on voit ce qui doit devenir un token de theming (couleurs, typo, radius…) et ce qui reste structurel.
2. Anticipe le theming dès la navbar CNT : si tu la codes avec des variables CSS / tokens (couleurs de marque, police) plutôt que des valeurs Tailwind en dur, l'export vers clyro-blocks sera quasi gratuit — la structure devient le bloc, les tokens deviennent le thème. Si tu codes tout en dur, tu referas le travail à l'export.
3. Point pratique : je n'ai pas trouvé le repo CNT Patrimoine en local (rien dans Mes projets ni Mon workflow). S'il est déployé sur Vercel, le code existe quelque part — quand tu voudras qu'on attaque la navbar, dis-moi où il vit (ou clone-le), et idéalement ouvre une session Claude Code directement dans ce dossier-là, puisque c'est là que le travail se fera.
Le chantier theming de clyro-blocks deviendra ensuite une spec à part entière (comme on avait reporté en v1) — la navbar CNT servira de premier cas réel pour la dimensionner.
